# 모바일 웹 커뮤니티 서비스 요구사항 정의서

## 개요

- **서비스명**: Community (가칭)
- **형태**: 모바일 웹 (Mobile Web, 반응형 / 모바일 우선)
- **기술 스택**: Next.js (App Router), Supabase (Auth / Database / Storage), Tailwind CSS, Vercel (배포)
- **하단 탭 네비게이션**: 홈(피드) · 내정보(프로필) · 설정 (3개 고정)
- **문서 버전**: v1.0 (2026-07-05)

## 2. 각 기능 상세 요구사항

### 2.1 회원가입
- 이메일 + 비밀번호로 가입한다. (Supabase Auth)
- 입력 항목: 이메일, 비밀번호, 닉네임.
- 유효성 검증: 이메일 형식, 비밀번호 최소 8자, 닉네임 2~20자.
- 닉네임은 중복 불가(고유값)로 처리한다.
- 가입 성공 시 `profiles` 레코드를 자동 생성한다. (트리거 또는 가입 직후 insert)
- 이메일 인증 사용 여부는 Supabase 설정에 따른다. (MVP는 미사용 가능)

### 2.2 로그인
- 이메일 + 비밀번호로 로그인한다.
- 실패 시 사유를 명확히 안내한다. (자격 증명 오류 등)
- 로그인 성공 시 세션을 유지하고 홈(피드)으로 이동한다.
- 로그인 상태는 Supabase 세션(쿠키 기반)으로 관리한다.

### 2.3 로그아웃
- 설정 화면에서 로그아웃할 수 있다.
- 세션을 종료하고 로그인 화면으로 이동한다.

### 2.4 글 작성
- 로그인한 사용자만 작성할 수 있다.
- 입력 항목: 제목(선택), 본문(필수).
- 본문 최대 길이 제한(예: 2,000자)을 둔다.
- 작성자, 작성 시각을 자동 기록한다.
- 작성 성공 시 상세 화면 또는 피드로 이동한다.

### 2.5 글 목록 (피드)
- 홈 탭에서 전체 글을 최신순으로 노출한다.
- 각 항목: 작성자 닉네임/프로필 이미지, 제목/본문 미리보기, 좋아요 수, 댓글 수, 작성 시각.
- 무한 스크롤 또는 페이지네이션으로 성능을 확보한다.
- 항목 탭 시 상세 화면으로 이동한다.

### 2.6 글 상세 보기
- 글 전체 내용과 작성자 정보를 표시한다.
- 댓글 목록, 좋아요 버튼/수를 함께 표시한다.
- 작성자 정보 탭 시 해당 유저 프로필로 이동한다.
- 본인 글일 경우 수정/삭제 메뉴를 노출한다.

### 2.7 글 수정 / 삭제 (권장)
- 본인 글만 수정/삭제 가능하다. (RLS로 강제)
- 삭제 시 연관 댓글/좋아요도 함께 정리한다. (ON DELETE CASCADE)

### 2.8 댓글
- 로그인한 사용자만 작성할 수 있다.
- 글 상세 화면에서 댓글을 작성/조회한다.
- 각 댓글: 작성자, 내용, 작성 시각.
- 본인 댓글은 삭제할 수 있다. (RLS로 강제)

### 2.9 좋아요
- 로그인한 사용자만 좋아요할 수 있다.
- 한 사용자는 한 글에 한 번만 좋아요 가능하다. (유니크 제약)
- 좋아요/취소를 토글로 처리한다.
- 좋아요 수를 실시간에 가깝게 반영한다. (낙관적 업데이트 권장)

### 2.10 내 프로필
- 내정보 탭에서 본인 프로필을 조회한다.
- 표시 항목: 닉네임, 프로필 이미지, 내가 쓴 글 목록.
- 내가 쓴 글 항목 탭 시 상세 화면으로 이동한다.

### 2.11 프로필 수정
- 닉네임, 프로필 이미지를 수정할 수 있다.
- 프로필 이미지는 Supabase Storage에 업로드하고 URL을 저장한다.
- 닉네임 변경 시 중복 검사를 수행한다.

### 2.12 다른 유저 프로필 보기
- 피드/상세의 작성자 정보를 통해 다른 유저 프로필로 진입한다.
- 표시 항목: 닉네임, 프로필 이미지, 해당 유저가 쓴 글 목록.
- 본인 프로필과 달리 수정 UI는 노출하지 않는다.

### 2.13 설정
- 계정 정보(이메일 등)를 표시한다.
- 로그아웃 버튼을 제공한다.
- (확장) 회원 탈퇴, 테마, 알림 설정 등을 추가할 수 있다.

### 2.14 공통 / 비기능 요구사항
- **인증 가드**: 비로그인 사용자는 작성/댓글/좋아요/프로필 수정 불가. 시도 시 로그인으로 유도한다.
- **권한(RLS)**: Supabase Row Level Security로 본인 데이터만 수정/삭제 가능하도록 강제한다.
- **반응형**: 모바일 우선, 최대 폭 제한(예: 480px) 컨테이너로 데스크톱에서도 자연스럽게 표시.
- **로딩/에러 처리**: 각 화면에 로딩 상태와 에러 안내를 제공한다.
- **접근성**: 버튼/입력 요소에 적절한 라벨 제공.

## 3. 사용자 흐름 (User Flow)

### 3.1 최초 진입 / 인증
```
앱 접속
 └─ 세션 있음? ─── 예 ──▶ 홈(피드)
        └─ 아니오 ──▶ 로그인 화면
                        ├─ 로그인 성공 ──▶ 홈(피드)
                        └─ 회원가입 링크 ──▶ 회원가입 ──▶ 성공 ──▶ 홈(피드)
```

### 3.2 글 작성 흐름
```
홈(피드) ──▶ [글쓰기] 버튼 ──▶ 글 작성 화면
   └─ 본문 입력 ──▶ [등록] ──▶ 저장 성공 ──▶ 글 상세(또는 피드 갱신)
```

### 3.3 글 읽기 / 상호작용 흐름
```
홈(피드) ──▶ 글 항목 탭 ──▶ 글 상세
   ├─ [좋아요] 토글 ──▶ 좋아요 수 갱신
   ├─ 댓글 입력 ──▶ [등록] ──▶ 댓글 목록 갱신
   └─ 작성자 탭 ──▶ 유저 프로필
```

### 3.4 프로필 흐름
```
내정보 탭 ──▶ 내 프로필 (닉네임/이미지/내 글)
   ├─ [프로필 수정] ──▶ 닉네임·이미지 변경 ──▶ 저장 ──▶ 프로필 갱신
   └─ 내 글 항목 탭 ──▶ 글 상세

(다른 유저) 피드/상세 작성자 탭 ──▶ 유저 프로필 (조회 전용)
```

### 3.5 로그아웃 흐름
```
설정 탭 ──▶ [로그아웃] ──▶ 세션 종료 ──▶ 로그인 화면
```

## 5. 데이터 개요

Supabase(PostgreSQL) 기준 핵심 테이블입니다. `auth.users`는 Supabase Auth가 관리하며, 서비스 데이터는 아래 테이블로 구성합니다.

### 5.1 테이블 요약

#### `profiles` — 사용자 프로필
| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | uuid (PK) | `auth.users.id` 참조 |
| `nickname` | text (unique) | 닉네임 (2~20자, 고유) |
| `avatar_url` | text (nullable) | 프로필 이미지 URL (Storage) |
| `created_at` | timestamptz | 생성 시각 |

#### `posts` — 게시글
| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | uuid (PK) | 게시글 ID |
| `author_id` | uuid (FK → profiles.id) | 작성자 |
| `title` | text (nullable) | 제목 |
| `content` | text | 본문 (필수) |
| `created_at` | timestamptz | 작성 시각 |
| `updated_at` | timestamptz | 수정 시각 |

#### `comments` — 댓글
| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | uuid (PK) | 댓글 ID |
| `post_id` | uuid (FK → posts.id, ON DELETE CASCADE) | 대상 글 |
| `author_id` | uuid (FK → profiles.id) | 작성자 |
| `content` | text | 내용 |
| `created_at` | timestamptz | 작성 시각 |

#### `likes` — 좋아요
| 컬럼 | 타입 | 설명 |
|------|------|------|
| `post_id` | uuid (FK → posts.id, ON DELETE CASCADE) | 대상 글 |
| `user_id` | uuid (FK → profiles.id) | 좋아요 누른 사용자 |
| `created_at` | timestamptz | 생성 시각 |
| | **PK (post_id, user_id)** | 중복 좋아요 방지(유니크) |

### 5.2 관계 (ERD 개요)
```
auth.users 1 ── 1 profiles
profiles   1 ──▶ N posts        (author_id)
profiles   1 ──▶ N comments     (author_id)
posts      1 ──▶ N comments     (post_id, CASCADE)
posts      1 ──▶ N likes        (post_id, CASCADE)
profiles   1 ──▶ N likes        (user_id)
```

### 5.3 파생 값 (집계)
- **좋아요 수**: `likes`에서 `post_id` 기준 count.
- **댓글 수**: `comments`에서 `post_id` 기준 count.
- 성능 최적화가 필요하면 count 캐시 컬럼 또는 뷰(`view`)를 사용한다.

### 5.4 RLS(행 수준 보안) 정책 개요
- `profiles`: 전체 조회 가능, 본인만 수정.
- `posts`: 전체 조회 가능, 로그인 사용자 작성, 작성자만 수정/삭제.
- `comments`: 전체 조회 가능, 로그인 사용자 작성, 작성자만 삭제.
- `likes`: 전체 조회 가능, 본인만 insert/delete.

### 5.5 Storage
- 버킷 `avatars`: 프로필 이미지 저장. 공개 읽기, 본인만 업로드/삭제.

## 부록: MVP 범위 제안
- **1차(MVP)**: 인증(가입/로그인/로그아웃), 글 작성/목록/상세, 댓글, 좋아요, 내 프로필/수정, 다른 유저 프로필, 설정(로그아웃).
- **2차(확장)**: 글 수정/삭제, 검색, 알림, 대댓글, 신고/차단, 무한 스크롤 최적화, 회원 탈퇴.
